根据对开源知识库系统的调研发现，跨向量数据库的数据迁移是一项成本不小的操作。

AnythingLLM 的官方文档明确指出，系统级别的向量数据库配置一旦更改，并不会自动将已有的向量数据从旧库迁移至新库。这种割裂源于底层向量数据库在管理索引结构（如 HNSW、IVF 聚类图）以及文档内部 ID 映射体系上的异构性。如果企业最初选择了轻量级的本地 LanceDB 并在数月后希望平滑升级至分布式的 Milvus，由于旧有的向量实体 ID 无法与新的内存布局对接，唯一稳妥的方案是触发系统指令，将原有文档语料库在新的空间中全部执行一次重嵌入（Re-embedding）过程。[^1]

同样地，对于 Dify 环境，在已经存在业务数据的生产集群中变更 `VECTOR_STORE` 环境变量，会导致原有的知识库检索能力瞬间失效。企业如果必须进行底层引擎更换，往往需要动用外部 ETL（Extract, Transform, Load）工程脚手架，将原始文本、前置生成的浮点向量数组连同 Metadata 重新序列化并写入新的数据库实例。[^2]

因此，在系统的初始生命周期审慎评估数据增长规模并一次性选定底层向量方案，依然是架构师不可逾越的必修课。
